# Shipped with known gap — PR #10589

PR #10589 merged with 10 unresolved adversarial concern(s) that survived all gates without an explicit ConcernResolution. Future planners / reviewers should treat these as known gaps until either addressed in a follow-up PR or explicitly accepted.

## Unresolved concerns

- **HIGH** `PLAN-ASSUMP-001` (raised in `plan` / `assumption_surfacer`): Helper validity: assumes `findBorderShorthandConflicts` in `src/ui/src/test/` correctly detects border shorthand/longhand conflicts and handles edge cases (e.g., `border: none`, `border: inherit`, variable values, multi-value shorthand compositions). Mechanism assumption—tool behavior unverified.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-002` (raised in `plan` / `assumption_surfacer`): CSS decomposition: assumes each base `border: "X"` value can be correctly split into `borderWidth`, `borderStyle`, `borderColor` without loss or ambiguity (e.g., `"1px solid #000"` → three separate properties). Mechanism assumption—CSS parser logic or manual mapping must be defined and validated.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-003` (raised in `plan` / `assumption_surfacer`): Search completeness: issue confirms four files but does not indicate whether a full codebase grep was run. Other components may have the same pattern outside these four locations.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-004` (raised in `plan` / `assumption_surfacer`): Reproducibility: issue states StreamCard variants 'should be reproducing' the React warning but does not confirm the warning is actively triggered in current codebase. Fix may be necessary but reproduction path unclear.
  - _must_address_by_: `planner`
- **LOW** `PLAN-ASSUMP-005` (raised in `plan` / `assumption_surfacer`): Variant homogeneity: assumes all variants of each component's style map differ only in `borderColor` and share the same `borderWidth`/`borderStyle`. If some variants override these too, the base decomposition strategy may differ per file.
  - _must_address_by_: `implementation`
- **CRITICAL** `SPEC-JUDGE-001` (raised in `plan` / `spec_judge`): AC #5 says render tests should assert computed border-width/style/color 'match their pre-change values' but provides no concrete expected values. The plan narrative gives some (e.g., stageNodeBase='2px solid', stageBadge='1px solid') but not all, and the AC itself lists no numerics. A test writer cannot write a failing test without reading source files to extract expected values and guessing where missing ones come from. Rephrase as: 'Render tests assert computed borders match [enumerated expected values for each component]' e.g., stageNodeBase: borderWidth='2px', borderStyle='solid', borderColor=undefined; stageBadge: borderWidth='1px', borderStyle='solid', borderColor=undefined; pill: borderWidth=?, borderStyle=?, borderColor=theme.border; etc.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-002` (raised in `plan` / `spec_judge`): AC #3 (BugReportPanel filter toggle) and AC #4 (IssueHistoryPanel preset change) assume the React 'conflicting property is set' console.error is currently triggering in the codebase. The plan claims 'two live React console.error collisions' but pending concern [PLAN-ASSUMP-004] notes reproducibility is unconfirmed — the issue states 'should be reproducing' but does not confirm the warning is actively emitted. If the warning does not trigger in the current render flow, these tests pass vacuously (zero errors in a case that never generated errors). Verify that these specific interactions actually emit the warning before merge, or add a test setup that simulates the shorthand/longhand conflict.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-003` (raised in `plan` / `spec_judge`): AC #1 ('test_no_border_shorthand_longhand_conflicts fails on main') depends on P1 (shared style reader) being correct, but the reader does not yet exist. The plan creates it in P1 with three test cases, but those tests (base+variant collision detection, borderRadius unaffected, template-literal edge cases) do not cover all CSS border decomposition edge cases or all variant patterns in the four target files. If the reader has a latent bug (e.g., misses spreads, or incorrectly decomposes 'border: none' / 'border: inherit' / multipart values), AC #1 could pass on main vacuously (reader reports no conflicts) and remain green after the fix (false negative). Add an AC that the reader correctly decomposes at least [specific examples: '2px solid', '1px solid', '2px solid theme.border'] to the three longhand properties.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-004` (raised in `plan` / `spec_judge`): AC #5 assumes all four components' variants differ only in `borderColor` and share the same width/style (pending concern [PLAN-ASSUMP-005]). The plan notes out-of-scope conflict at StreamCard:130 where `border` mixes with `borderLeft` (shorthand↔shorthand) and one variant drops `borderLeft` entirely. If other components have similar non-homogeneous patterns (e.g., one variant overrides width, another overrides style), the AC's assumption breaks. Add validation: list which variants override which properties for each of the four components, or assert the reader found no width/style overrides in any variant.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-005` (raised in `plan` / `spec_judge`): AC #2 guards against silent failure by asserting sentinels are found, but only names six bases. The plan targets four files and P1 creates a collision finder; does the finder also validate that no other files in the codebase have the same pattern? If search is incomplete (pending concern [PLAN-ASSUMP-003]), the fix addresses only the named four and latent sites remain. AC #2 should either state 'and a full codebase scan found no other [base + variant] pairs mixing border shorthand with border* longhand' or accept that the source-level pin is a 'these four files only' guard.
  - _must_address_by_: `implement`
