# Shipped with known gap — PR #11172

# Shipped with known gap — PR #11172

PR #11172 merged with 10 unresolved adversarial concern(s) that survived all gates without an explicit ConcernResolution. Future planners / reviewers should treat these as known gaps until either addressed in a follow-up PR or explicitly accepted.

## Unresolved concerns

- **CRITICAL** `PLAN-ASSUMP-001` (raised in `plan` / `assumption_surfacer`): The core_python filter explicitly excludes agents/**, but the python filter includes it. The audit job only checks core_python || ci, not python. A PR changing only agents/console/decisions/** sets python=true but core_python=false and ci=false, causing the audit job to skip. The fix thus fails for the primary attack vector it targets.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-002` (raised in `plan` / `assumption_surfacer`): Mechanism assumption: CI filter outputs and job trigger conditions are fragile. The assumption that needs.changes.outputs.python is a separate output and that the audit job's if: condition should also check it requires validation against the actual GitHub Actions filter behavior. Validate in a scratch repo or minimal spike before committing to this mechanism in the plan.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-003` (raised in `plan` / `assumption_surfacer`): The test test_ci_audit_job_runs_console_conformance only checks that the step exists and checkout has fetch-depth: 0. It does not assert that the job's if: condition actually fires for agents/** changes. The test passes green despite the triggering logic being broken for the primary scenario.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-004` (raised in `plan` / `assumption_surfacer`): The PR claims the audit job is 'the only job with fetch-depth: 0', but the arch job (ci.yml:293-301) also uses it. This factual error suggests incomplete design thinking about which job owns the ledger immutability check.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-005` (raised in `plan` / `assumption_surfacer`): The arch job already has fetch-depth: 0 and is arguably a more natural home for ARCH-0001 ledger immutability enforcement than the audit job, which doesn't include agents/** in its own filters either.
  - _must_address_by_: `planner`
- **HIGH** `SPEC-JUDGE-001` (raised in `plan` / `spec_judge`): AC 7 scope ambiguity: 'the ratchet asserting every top-level directory in `agents/`' is vague. Does this mean every subdirectory under `agents/` (e.g., `agents/console/`, `agents/other/`), or is it a shorthand for 'the `agents/` directory'? The plan states the ratchet is 'retargeted' to `core_python`, which implies checking all top-level directories in the repo against that filter (consistent with current behavior), not just `agents/` subdirectories. The AC should explicitly clarify: is the ratchet checking 'every top-level directory in the repo' or 'only subdirectories under `agents/`'? As written, it's ambiguous enough that two implementers might write different tests.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-002` (raised in `plan` / `spec_judge`): Pending concern PLAN-ASSUMP-001 (CRITICAL) flagged that the audit job checks `core_python || ci`, which doesn't cover agent-only PRs. The plan claims to fix this by ORing `console_ledger` into the condition. However, no AC explicitly verifies the OR syntax appears in the workflow. AC 1 checks the output is defined; AC 2 checks the condition evaluates true for a sample changeset. Together they *imply* the OR is in place (since AC 2 would fail if it weren't), but this is indirect. Given the CRITICAL severity of the pending concern, an explicit AC stating 'the `audit` job's `if:` condition includes `console_ledger` as an OR clause' would be more verifiable and confidence-building.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-003` (raised in `plan` / `spec_judge`): AC 5's test name `test_console_conformance_reachable_for_ledger_only_change` does not appear in the plan's task descriptions (P1 outlines the test concept but not the exact name). Test naming should be synchronized between the plan and AC to avoid mismatches during implementation.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-004` (raised in `plan` / `spec_judge`): Risk 2 (audit job fails on ledger PRs due to unrelated checks) is identified and mitigation proposed ('verify audit job green on this PR itself'), but no AC explicitly captures this verification. AC 9 (`make quality` passes) might implicitly cover it if audit steps are part of `make quality`, but it's not stated. An explicit AC verifying audit-job-specific behavior would clarify the scope of the quality check.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-005` (raised in `plan` / `spec_judge`): The plan states 'raise `EXEMPT_PATHS_MAX` deliberately', but no AC explicitly verifies this. AC 7 requires the ratchet test to pass (which implies the count was raised), but this is indirect. An AC stating '`EXEMPT_PATHS_MAX` is increased to match the number of exempt paths and documented' would be more explicit.
  - _must_address_by_: `implement`
