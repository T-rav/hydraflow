# Shipped with known gap — PR #11448

PR #11448 merged with 8 unresolved adversarial concern(s) that survived all gates without an explicit ConcernResolution. Future planners / reviewers should treat these as known gaps until either addressed in a follow-up PR or explicitly accepted.

## Unresolved concerns

- **HIGH** `PLAN-ASSUMP-001` (raised in `plan` / `assumption_surfacer`): DiagnosticLoop workspaces consumption is not traced. The issue states 'needs a read of how `self._workspaces` is consumed downstream' — we don't yet know if `None` silently no-ops a path, raises an error, or passes through correctly. The parameter name may also be `workspaces` (plural) not `workspace` (singular).
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-002` (raised in `plan` / `assumption_surfacer`): Port key names are assumed but unverified: `auto_diagnoser`, `refine_llm`, `workspace`. Specifically, the issue states `refine_llm` has 'no equivalent port at all' currently — we may need to seed this from config or a different source, not assume it's in `ports`.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-003` (raised in `plan` / `assumption_surfacer`): Mechanism assumption: `ports.get(key)` returns the collaborator instance when the key exists, or `None` when absent. This is a subprocess/tool assumption about dict behavior and port-wiring convention — validate in a scratch scenario before committing to this pattern for all three sites.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-004` (raised in `plan` / `assumption_surfacer`): The issue references demonstrating 'previously-dead paths' via MockWorld scenarios but doesn't specify: (1) which specific code paths in each loop, (2) what inputs/state trigger them, or (3) whether existing scenario coverage already exercises them. The acceptance criterion is vague — 'a MockWorld scenario test (or existing coverage)'.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-005` (raised in `plan` / `assumption_surfacer`): For `SkillPromptEvalLoop`, the issue mentions the builder 'already monkey-patches `_run_corpus`/`_reconcile_closed_escalations` onto the instance' via `skill_corpus_runner`/`skill_reconcile_closed` ports. It's unclear whether `refine_llm` should follow the same pattern or be injected as a constructor parameter like the other two sites.
  - _must_address_by_: `next`
- **CRITICAL** `SPEC-JUDGE-001` (raised in `plan` / `spec_judge`): Draft AC #6 (diagnostic scenario test) asserts FakeWorkspace.create() and destroy() called, but provides no specification of what inputs, state, or triggering conditions reach the self._workspaces-gated path. Plan text says 'drive through a MockWorld scenario tick that reaches the...gated path' but the AC itself does not name which code paths, what preconditions, or what actions within the tick exercise this path. Implementer cannot write a failing test without reverse-engineering the production code.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-002` (raised in `plan` / `spec_judge`): AC assumes port key 'refine_llm' exists in the ports dict, but pending concern PLAN-ASSUMP-002 explicitly flags that refine_llm 'has no equivalent port at all currently'. AC does not include a verification or discovery step to confirm this port key exists or is seeded from an alternative source before forwarding it to the builder.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-003` (raised in `plan` / `spec_judge`): AC assumes self._workspaces is consumed by calling FakeWorkspace.create() and destroy(), but pending concern PLAN-ASSUMP-001 notes the consumption pattern 'is not traced' — plan states 'needs a read of how self._workspaces is consumed downstream'. Without prior verification, the diagnostic test could pass under wrong preconditions if the code silently no-ops, raises, or consumes workspaces differently than assumed.
  - _must_address_by_: `implement`
