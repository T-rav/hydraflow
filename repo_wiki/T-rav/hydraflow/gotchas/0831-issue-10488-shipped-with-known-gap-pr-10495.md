# Shipped with known gap — PR #10495

PR #10495 merged with 24 unresolved adversarial concern(s) that survived all gates without an explicit ConcernResolution. Future planners / reviewers should treat these as known gaps until either addressed in a follow-up PR or explicitly accepted.

## Unresolved concerns

- **HIGH** `PLAN-ASSUMP-001` (raised in `plan` / `assumption_surfacer`): Mechanism assumption: Can /api/pipeline be extended to expose stage-membership counts efficiently? Or does a separate count endpoint need to be built? Whether the extension is straightforward needs spiking.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-002` (raised in `plan` / `assumption_surfacer`): Acceptance criterion 'counts and cards never disagree' assumes count query and card query are synchronized. If they hit the endpoint at different times or via different code paths, an issue/PR could move stages between queries, causing divergence.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-003` (raised in `plan` / `assumption_surfacer`): Update mechanism is undefined. The issue says 'update as the pipeline changes' but does not specify: page reload only, polling interval, real-time WebSocket, or event-driven. This affects component design and complexity.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-001` (raised in `plan` / `assumption_surfacer`): Stage enumeration mechanism is unverified. Issue lists example stages ('triage, plan, implement, review, hitl, merged', 'whatever the current regions are') but does not specify implementation source. Planner must validate: are stages currently enumerable via hardcoded enum, data query, or other pattern? If no existing pattern, design choice (hardcode vs dynamic enumeration) affects architecture. Validate in spike before committing to implementation.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-ASSUMP-002` (raised in `plan` / `assumption_surfacer`): Filter logic parity between card and count queries needs validation. 'Counts and cards never disagree' assumes identical 'open' filtering, but filter logic could live in backend endpoint, frontend component, or separate count query—if paths diverge (e.g., one filters draft PRs, other doesn't), counts diverge from cards. Planner must verify: what defines 'open'? Is the filter centralized or replicated across code paths? Code review required before design.
  - _must_address_by_: `planner`
- **CRITICAL** `PLAN-RISK_SKEPTIC-001` (raised in `plan` / `plan_council_risk_skeptic`): PLAN-ASSUMP-002 is contradicted by the approach. The plan claims 'counts and cards cannot disagree' because both derive from the same `stageGroups`, but ASSUMP-002 flags that if card and count queries hit the endpoint at different times, an issue could move stages between queries. Clarify: Are badges and cards both reading from a single in-memory context object (immune to divergence), or is the plan assuming separate synchronous fetches? If the latter, the divergence risk is real.
  - _must_address_by_: `planner`
- **CRITICAL** `PLAN-RISK_SKEPTIC-002` (raised in `plan` / `plan_council_risk_skeptic`): PLAN-ASSUMP-003 (Update mechanism undefined) is unresolved. The plan says counts 'update as the pipeline changes' but does not specify the trigger: page reload only, polling, WebSocket, or event-driven. If `StreamView` only renders once on mount, badges become stale immediately. Verify: Does `StreamView` currently re-fetch or subscribe to `/api/pipeline` changes? If not, add a polling or subscription mechanism or accept that badges are display-only-on-load.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-RISK_SKEPTIC-003` (raised in `plan` / `plan_council_risk_skeptic`): Stage enumeration mechanism is unverified (PLAN-ASSUMP-001). The plan assumes `renderFlowStage` exists at StreamView.jsx:374 and iterates over all current stages. Verify this function exists in the codebase and that it handles stage discovery dynamically or is hardcoded to a fixed set. If stages are dynamic and this function doesn't discover new stages, counts for new stages won't render.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-RISK_SKEPTIC-004` (raised in `plan` / `plan_council_risk_skeptic`): PR detection logic is underspecified. The test says 'A group of 3 issues, 2 carrying a pr' but does not specify the shape of `issue.pr`. Is it a boolean, object, string? Is it `null` or `undefined` when absent? The util must define detection logic clearly (e.g., `!!issue.pr`, `issue.pr !== null`). Missing specification risks implementation bugs when `issue.pr` is falsy-but-not-null.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-RISK_SKEPTIC-005` (raised in `plan` / `plan_council_risk_skeptic`): Badge rendering location is unverified. The plan says 'render a per-region badge inside `renderFlowStage`' but does not confirm this function exists or that inserting badges will not break layout. Verify that `StreamView.jsx:374` contains a `renderFlowStage` function and that adding badges in that context is structurally safe.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-RISK_SKEPTIC-006` (raised in `plan` / `plan_council_risk_skeptic`): Reactivity mechanism is assumed but not detailed. The test 'Updating the context snapshot re-renders the badge with the new number' expects the component to detect context changes, but the plan does not specify how: `useEffect` subscription, React.useContext reactivity, or manual callback. Without this, badges may not update when pipeline state changes. Verify the subscription mechanism or add explicit polling.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-RISK_SKEPTIC-007` (raised in `plan` / `plan_council_risk_skeptic`): `StreamView.jsx` is already 741 lines. Adding badge rendering logic + count util call could push it further. No line-count estimate is provided. Estimate the delta and verify it does not violate any module-size conventions or readability thresholds.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-RISK_SKEPTIC-008` (raised in `plan` / `plan_council_risk_skeptic`): Responsive design is unaddressed. The plan mentions 'narrow horizontal strip' with `flexShrink: 0` and `whiteSpace: 'nowrap'` but does not test mobile or narrow-screen layouts. Counts (e.g., '11 / 8') may overflow on small screens. Include a responsive test or confirm the design gracefully degrades on mobile.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-RISK_SKEPTIC-009` (raised in `plan` / `plan_council_risk_skeptic`): Defensive null/undefined handling is incomplete. The plan tests 'An empty group reports 0 / 0' and mentions defensive zeros for missing `issues`, but does not test what happens if `group` itself is `null` or `undefined`. Extend the util to guard against missing group objects, not just missing `issues` field.
  - _must_address_by_: `planner`
- **LOW** `PLAN-RISK_SKEPTIC-010` (raised in `plan` / `plan_council_risk_skeptic`): Existing badge-component pattern is cited (badge styles precomputed at module scope) but no example or link is provided. Verify that this plan aligns with existing badge conventions and does not duplicate a reusable badge component. If a badge component already exists, use it rather than inline styling.
  - _must_address_by_: `planner`
- **CRITICAL** `SPEC-JUDGE-001` (raised in `plan` / `spec_judge`): AC 6 ('Updating context snapshot re-renders badge') is untestable without specifying the update mechanism. The plan claims counts 'update as the pipeline changes' but does not define the trigger: is it a React context change, prop update, polling subscription, or WebSocket event? Without this, the test 'Updating the context snapshot with different pipelineIssues causes badge re-render' cannot be written—you don't know what action to take to force the update or how to verify the re-render happened. PLAN-RISK_SKEPTIC-002 flags this as CRITICAL but the AC proceeds as if it's solved.
  - _must_address_by_: `implement`
- **CRITICAL** `SPEC-JUDGE-002` (raised in `plan` / `spec_judge`): AC divergence contradiction. AC 'Counts come from the same stageGroups the cards render' assumes in-memory derivation (safe from divergence), but PLAN-RISK_SKEPTIC-001 correctly points out that if badges and cards hit `/api/pipeline` at different times via separate fetches, an issue could move stages between queries. The plan does not clarify: are badges reading a shared React Context/in-memory snapshot (guaranteed consistent), or separate synchronous calls (divergence-possible)? This contradiction makes 'counts and cards never disagree' unprovable.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-003` (raised in `plan` / `spec_judge`): AC 2 and AC 4 (PR count detection) are underspecified. They state 'number of issues where the pr field is defined' but do not define what 'defined' means. Is it `!!issue.pr` (truthy), `issue.pr !== null`, `issue.pr !== undefined`, or a shape check? The util must specify detection logic, but PLAN-RISK_SKEPTIC-004 notes this is missing. A test case 'When 2 of 3 issues have an associated pr' is concrete in count but not in the detection rule, risking implementation mismatches (e.g., falsy-but-not-null values treated as missing).
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-004` (raised in `plan` / `spec_judge`): Stage enumeration mechanism (AC 9, AC 10) is unverified. The plan assumes terminal stages 'hitl' and 'merged' exist and are discoverable via the pipeline flow rendering logic. PLAN-RISK_SKEPTIC-003 flags this: are stages hardcoded, fetched dynamically, or driven by `stageGroups` keys? Without confirming these stage names are valid in the current codebase, AC 9 ('Terminal regions hitl and merged each render their own badge') and AC 10 ('total includes hitl and merged') cannot be reliably tested—a test could pass with mocked data but fail against real pipeline data if these stages are named differently or don't exist.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-005` (raised in `plan` / `spec_judge`): AC 11 (implementation source) assumes `renderFlowStage` exists at `StreamView.jsx:374` and `toStreamIssue` is at line 290, but these locations are unverified. PLAN-RISK_SKEPTIC-005 notes this: the plan must confirm the function and line numbers exist before committing. If the function is named differently, located elsewhere, or has changed signature since the plan was drafted, the AC 'Count values derived from stageGroups at StreamView.jsx:374' becomes an incorrect specification that will guide implementers to the wrong code location.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-006` (raised in `plan` / `spec_judge`): Reactivity/subscription mechanism (AC 6) lacks implementation detail. The plan does not specify how `StreamView` detects pipeline changes to trigger badge re-renders. PLAN-RISK_SKEPTIC-006 identifies this: does `StreamView` currently subscribe to context changes via `useEffect`, React.useContext reactivity, WebSocket listeners, or polling? Without this, the test 'updating context causes re-render' is unwritable—you need to know the subscription contract to drive the update in a test. If `StreamView` currently only fetches once on mount, badges are display-only-on-load and AC 6 is unachievable.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-007` (raised in `plan` / `spec_judge`): Defensive null/undefined handling (AC 8) is incomplete. The AC tests 'when issues field is undefined, display 0' but PLAN-RISK_SKEPTIC-009 correctly identifies that the util must also guard against the group object itself being `null` or `undefined`, not just the `issues` field. The test does not cover `pipelineCounts(null)` or `pipelineCounts({})` (group with no `issues` property). An incomplete defensive spec risks runtime crashes if partial payloads arrive.
  - _must_address_by_: `implement`
- **MEDIUM** `SPEC-JUDGE-008` (raised in `plan` / `spec_judge`): Module size boundary is unquantified. StreamView is already 741 lines; adding badge rendering + count util calls could exceed readability thresholds. The plan notes this but provides no line-count estimate or confirmation that the delta won't violate conventions. PLAN-RISK_SKEPTIC-007 flags: estimate the delta and verify against any module-size rules in the codebase before committing.
  - _must_address_by_: `implement`
- **LOW** `SPEC-JUDGE-009` (raised in `plan` / `spec_judge`): Badge component reuse not verified. The plan mentions 'Badge styles precomputed at module scope (repo convention: no style spreads inside a map)' but does not confirm whether a reusable badge component already exists. If one does, the ACs should require using it rather than inline styling. Verify against existing UI conventions before implementation.
  - _must_address_by_: `implement`
