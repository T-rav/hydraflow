# Shipped with known gap — PR #10928

PR #10928 merged with 25 unresolved adversarial concern(s) that survived all gates without an explicit ConcernResolution. Future planners / reviewers should treat these as known gaps until either addressed in a follow-up PR or explicitly accepted.

## Unresolved concerns

- **HIGH** `PLAN-ASSUMP-001` (raised in `plan` / `assumption_surfacer`): Haven't verified all callers of `_load_audit_module` exist. A grep search is needed before the refactor to ensure scope is complete and nothing breaks downstream.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-002` (raised in `plan` / `assumption_surfacer`): docs/wiki/gotchas.md documents this anti-pattern but the issue doesn't specify the exact recommended refactoring convention (e.g., should private version remain, be removed, or stay for backwards compatibility). Planner should consult the wiki entry first.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-ASSUMP-003` (raised in `plan` / `assumption_surfacer`): Unknown whether there are other private exports in prompt_fitness.py or sibling modules following the same coupling anti-pattern. Should this fix address only `_load_audit_module`, or is a broader audit needed?
  - _must_address_by_: `planner`
- **CRITICAL** `PLAN-TESTER-001` (raised in `plan` / `plan_council_tester`): No automated test prevents silent re-introduction of direct `_load_audit_module()` calls within `src/prompt_fitness.py`. The acceptance criterion states 'No call to _load_audit_module() remains in src/prompt_fitness.py beyond the delegate's own definition,' but this is listed as a test goal without naming a test that would fail if violated. A developer could accidentally add a call to the private name and the suite would still pass. Either a grep-based CI check or a test that inspects source code must enforce this.
  - _must_address_by_: `planner`
- **CRITICAL** `PLAN-TESTER-002` (raised in `plan` / `plan_council_tester`): No automated test prevents cross-module imports of `_load_audit_module` anywhere in the repo. Acceptance criterion 4 states 'No cross-module import of _load_audit_module remains in the repo,' but grep/manual review is not automated. A developer could add `from src.prompt_fitness import _load_audit_module` in a test or sibling module and no test would fail. Need a CI check or architecture test that fails on this pattern.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-TESTER-003` (raised in `plan` / `plan_council_tester`): No test verifies the delegate pattern itself — that `_load_audit_module()` actually calls the public function rather than duplicating its body. Both could independently call `importlib.util.spec_from_file_location()` and tests could still pass. Need a test that inspects the private implementation or verifies both functions return the same object, not just equivalent data.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-TESTER-004` (raised in `plan` / `plan_council_tester`): The claim 'The private name resolves through the public one rather than a diverged copy' is described as comparing `PROMPT_REGISTRY` length, which is insufficient. Two independently-loaded modules could have the same registry size. Need a test verifying identity (same object reference) or that the private function literally delegates: `return load_audit_module()`.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-TESTER-005` (raised in `plan` / `plan_council_tester`): The test for 'fitness_summary() still returns a PromptFitness with non-zero discovered_modules' is not named. It is listed as a must-stay-green test in P1, but no test file or assertion is specified. If this is implicit in `test_prompt_fitness.py`, clarify which test. If not covered, a regression test should explicitly exercise this call path post-rename.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-TESTER-006` (raised in `plan` / `plan_council_tester`): Error handling edge cases are not discussed. What if `scripts/audit_prompts.py` doesn't exist, can't be parsed, or `importlib.util.spec_from_file_location()` raises an exception? The plan says the body is unchanged, but does the existing code handle these cases? Should new regression test verify error behavior is preserved?
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-TESTER-007` (raised in `plan` / `plan_council_tester`): The test `test_issue_10859.py` import swap is claimed to still pass, but the specific new assertions that verify the import works are not described. A bare `import load_audit_module` statement could fail silently at module scope if the name is not exported. Specify how the new import is verified at test parse time, not just at assertion time.
  - _must_address_by_: `planner`
- **LOW** `PLAN-TESTER-008` (raised in `plan` / `plan_council_tester`): The plan relies on `test_src_does_not_import_scripts.py` to prevent module-scope `from scripts.audit_prompts import ...` (which would break the container). Confirm this test actually fails if such an import is added at module scope, not just if a `scripts` import occurs anywhere (e.g., inside a function). Verify the test's regex or import-time inspection is precise.
  - _must_address_by_: `planner`
- **CRITICAL** `PLAN-RISK_SKEPTIC-001` (raised in `plan` / `plan_council_risk_skeptic`): PLAN-ASSUMP-001 (unresolved from planning phase): Callers of `_load_audit_module` have not been enumerated. The plan states 'update all in-module call sites' but does not show grep results proving scope is complete. If external callers exist (tests in other projects, plugins, scripts not yet merged), the back-compat claim fails. Required: run `grep -r '_load_audit_module' --include='*.py'` across the repo and verify the complete call graph before proceeding.
  - _must_address_by_: `planner`
- **HIGH** `PLAN-RISK_SKEPTIC-002` (raised in `plan` / `plan_council_risk_skeptic`): PLAN-ASSUMP-003 (unresolved): The plan treats `_load_audit_module` as an isolated instance, but does not audit `src/prompt_fitness.py` or sibling modules for OTHER private exports with the same cross-module-import anti-pattern. Is this one-shot fix sufficient, or is there a systemic cleanup that should be done together? Fixing one instance while others exist leaves the anti-pattern partially in place and may invite future confusion. Clarify scope: is `_load_audit_module` the only offender in this module?
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-RISK_SKEPTIC-003` (raised in `plan` / `plan_council_risk_skeptic`): PLAN-ASSUMP-002 (unresolved): The plan does not show consultation of `docs/wiki/gotchas.md`, which the CLAUDE.md references as documenting this anti-pattern and possibly specifying a recommended refactoring convention. The rename-plus-delegate pattern mirrors `repo_wiki.py`, but the wiki entry may specify a different or more nuanced approach. Verify the wiki guidance before finalizing.
  - _must_address_by_: `planner`
- **MEDIUM** `PLAN-RISK_SKEPTIC-004` (raised in `plan` / `plan_council_risk_skeptic`): Back-compat assumption untested: The plan claims the private-name delegate ensures 'unknown external caller keeps working,' but does not verify that external callers actually exist or what they expect. If the only callers are the test and in-module sites (both of which can be migrated), the back-compat path may be dead code—wasting maintenance surface for a hypothetical caller. Either enumerate external callers or justify the belt-and-suspenders approach explicitly.
  - _must_address_by_: `planner`
- **LOW** `PLAN-RISK_SKEPTIC-005` (raised in `plan` / `plan_council_risk_skeptic`): The plan relies on `importlib.util.spec_from_file_location` to work correctly across the container boundary. This is well-documented Python standard library, and the architecture test `test_src_does_not_import_scripts.py` appears to validate the pattern. Risk is low, but if the container build ever changes, this becomes a hidden constraint. Document the dependency clearly in the regression test comment.
  - _must_address_by_: `planner`
- **CRITICAL** `SPEC-JUDGE-001` (raised in `plan` / `spec_judge`): AC3 and AC4 use grep checks to verify absence of the anti-pattern (_load_audit_module calls and cross-module imports), but these checks are not automated in the test suite. Required: run `grep -r '_load_audit_module' --include='*.py'` and verify the complete list of call sites.
  - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-003` (raised in `plan` / `spec_judge`): AC2 (delegate verification) is insufficient.   - _must_address_by_: `implement`
- **HIGH** `SPEC-JUDGE-004` (raised in `plan` / `spec_judge`): PLAN-ASSUMP-003 (scope audit) is unresolved: the plan does not audit whether `_load_audit_module` is the only private export in `src/prompt_fitness.py` (or sibling modules) following the same cross-module-import anti-pattern.
